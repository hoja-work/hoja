# Automatic team cycle cadence — approval plan (no implementation yet)

## Scope

The user chose automatic team cadence rather than manual cycle creation, then delegated remaining policy decisions to the agent and asked for no more questions. Phase one will opt in per team, require an admin to choose a weekday, and use Linear's documented defaults: one-week duration, no cooldown, two upcoming cycles. It will not claim full Linear equivalence: configurable ranges, auto-assignment/rollover, manual date edits, parent-team inheritance, capacity forecasts and historical backfill are separate capabilities. The first enabled Current cycle starts on the team's present local date; later cycles align to the chosen weekday. No implementation or original account mutation occurs before plan approval.

## Schema

`hoja_server/schema.graphql` Team (`#L138-L154`) exposes timezone, cycles and activeCycle; Cycle (`#L177-L188`) exposes number/name/start/end/completed/progress/team. Query (`#L65-L67`) offers cycles and cycle(id); Mutation (`#L84-L102`) has no cycleCreate/update or team cadence settings. `hoja_server/db.py#L163-L181` team stores timezone/active_cycle_id but no recurrence; `db.py#L373-L390` cycle stores org/team/number, ISO-like text timestamps, progress and unique(team_id,number), not overlap constraints. `writer.py#L112-L123` validates issue cycle references in the same organization and team. There is no current cadence validation, permission or date-time boundary contract. Preserve wire-facing Linear GraphQL names; add fields/mutations without renaming existing fields.

## Storage

`store.py#L655-L682` reads team cycles ordered by number and filters cycles by organization/team. `store.py#L1078-L1124` derives isActive from team.active_cycle_id; isNext chooses the next numbered cycle (or first with no active). `resolvers.py#L325-L334,#L379-L392` exposes the reads. `db.py#L560-L580` runs ordered migrations, `db.py#L617-L681` seeds timezone UTC and no cycles; `app.py#L47-L105` creates engine/store/writer/auth but no scheduling worker. No Writer method creates or rotates cycles. Unique(team_id,number) stops duplicate numbers but not overlapping windows or partial concurrent writes. The new lifecycle must transact settings, cycle rows, and active pointer atomically and handle retries/restart.

## Linear reference

Authenticated read-only t2 `/cloverve/team/CLO/cycles`, `/cloverve/team/CLO/cycle/upcoming`, and `/cloverve/settings/teams/CLO/cycles` were inspected. Team settings show Enable cycles on; 1-week duration (options 1–8 weeks), no cooldown (none/1–3), Tuesday start, two pre-created upcoming cycles (options 1/2/3/4/6/8/10/12/15), and automation toggles Active issues & due date off, Started/Completed on. The display read “Current cycle is Sep 29 – Oct 6, next cycle begins Oct 6.” The weekday control reported only workspace owners/admins may modify team cycle settings. No external setting was changed and no transition was watched. Linear's public [Cycles documentation](https://linear.app/docs/use-cycles) says teams opt in, cycles begin at **12:01 AM** on the chosen weekday in the team's timezone, two upcoming cycles are the historical default, completed history is preserved, and disabling completes Current and removes Upcoming. It recommends enabling a short current cycle when starting mid-cycle. These docs are reference evidence; precise internals and permissions in this account are not observed.

## Decisions

1. **Enablement — resolved, reference-grounded:** off for existing/new Hoja teams until an admin opts in. The observed Linear switch is enabled for that account; its docs explicitly say enable in team settings. Migration must not silently create cycles.
2. **Start weekday — user-decided:** admin must select one of seven weekdays; never hardcode the observed team's Tuesday. Use persisted team IANA timezone, which defaults to UTC for seeded teams; reject unknown timezone.
3. **Initial interval — user delegated, agent recommends:** duration 1 week, cooldown 0, horizon 2 Upcoming (documented Linear defaults). No configuration UI for broader ranges in phase one.
4. **Midweek activation — user delegated, agent recommends:** create a short Current cycle immediately from 00:01 on the current **team-local day** until the next chosen weekday 00:01. If activation occurs on the chosen weekday at or after 00:01, start a full one-week Current; if before 00:01, start at 00:01 and show Upcoming until then. Store UTC instants, derive each local weekday boundary independently to handle DST; use half-open `[start,end)` intervals and never add 168 hours across DST. Display local calendar dates. Number initial Current 1 and subsequent cycles monotonically. No retroactive cycles.
5. **Generation/reconciliation — user delegated, agent recommends:** enabling creates Current (if due) and exactly two Upcoming in one transaction. A bounded server reconciliation on authenticated team cycle reads and on settings writes creates missing future slots/rotates due cycles; it catches up across a restart without a persistent in-process timer. An explicit scheduled maintenance command can later call the same idempotent reconciler. Do not write during anonymous/static requests. At most a bounded horizon is generated per call; if a team was offline many periods, advance through elapsed boundaries transactionally with a documented maximum batch/retry response, not an unbounded loop.
6. **Existing cycles and disablement — user delegated, agent recommends:** enabling rejects teams with existing non-archived cycles until they are explicitly reconciled; never renumber/delete fixture/manual records silently. Phase-one settings do **not** offer disable/reanchor after enablement, because those are data-changing operations with unresolved linked-issue semantics. The API returns a clear unsupported-action error rather than pretending to follow Linear's disable behavior. Plan a later guarded migration and disable flow (complete Current, archive Upcoming, reconcile issue associations) after specifying it independently.
7. **Issue automation — deferred explicitly:** do not auto-add, move, or roll over issues in phase one. The Current/Upcoming sidebar reflects real cycle records and manually associated issues only. This differs from Linear's enabled Started/Completed automations and must be disclosed in UI.

No critical phase-one policy choice remains unanswered: the user delegated the remaining choices. Any implementation that cannot uphold these conservative rules must return to plan approval rather than improvise a new default.

## Implementation plan

### Sequence and dependencies (dress rehearsal)

1. **Migration and constraints:** after inspecting live migration conventions, add per-team cadence enable flag, selected weekday, fixed versioned policy fields and anchor/effective instant (or a dedicated cadence table); keep existing teams disabled. Persist interval identity/anchor on cycles or derive uniquely from team + boundary, with an idempotency uniqueness constraint. Existing `cycle`/`team` readers remain backward compatible. Failure: migration aborts transaction and reports schema mismatch; no original database work before backup/approval.
2. **Pure boundary calculation:** accept an injectable UTC `now`, validated IANA timezone, weekday and fixed defaults. Convert to team local date; calculate local 00:01 boundaries for Current/Upcoming and convert each to UTC; reject nonexistent/ambiguous local times deterministically (00:01 typically avoids DST switches, but do not assume every timezone). Return ordered non-overlapping `[start,end)` intervals, stable numbers and display dates. Depends on step 1's stored anchor/policy. Failure: invalid timezone/day yields typed input error before any write.
3. **Transactional reconciler:** lock the team cadence row using backend-appropriate transaction semantics (SQLite writer serialization/BEGIN IMMEDIATE; PostgreSQL row lock if supported), check authorization for settings writes, query existing intervals, refuse conflicting legacy rows, insert missing bounded cycles idempotently, complete elapsed Current, update `active_cycle_id`, keep two Upcoming. Retry uniqueness conflicts by re-reading committed state; do not swallow other DB failures. Depends on steps 1–2. Return authoritative rows, never optimistic UI state. If catch-up exceeds bound, return explicit retry/progress status; do not create partial misleading view.
4. **GraphQL and startup integration:** add a team-scoped cadence-settings query and admin-only enable mutation; resolver uses authenticated org/team and returns persisted settings/cycles. Call the same reconciler at authenticated Current/Upcoming/cycle-list read boundary (or a dedicated ensure query), ensuring `Team.activeCycle` and `isActive`/`isNext` see a consistent snapshot. No global app startup write that can race on multiple workers. Existing GraphQL fields and CLI compatibility remain. Depends on step 3. Denied/missing team returns typed error; partial failure leaves prior committed cycles intact.
5. **Hoja UI:** in team Cycles settings/sidebar, show disabled opt-in state, weekday picker, explicit fixed defaults and an automation limitation notice. Admin submit is pending/disabled against duplicates; cancel leaves unchanged; on success refresh authoritative team Current/Upcoming and navigate only after receipt. Non-admin sees read-only settings and authorization notice. Preserve team-key navigation, keyboard focus, mobile layout and existing no-cycle empty state. Depends on step 4.
6. **Version/changelog and verification:** bump `VERSION` and `pyproject.toml`, update `CHANGELOG.md`, inspect diff against pre-existing dirty work, build frontend/compile backend/schema and run isolated end-to-end browser/API checks. User preference from this conversation: do not add/run unit tests. Do not commit/tag/release absent explicit release request. Depends on all previous steps.

### Ripples and breaking points

- New team settings affect seeding, migrations, organization switching, GraphQL Team serialization, CLI clients and sidebar; inspect each consumer before editing.
- Changing `isActive`/`isNext` could alter filters throughout issue/project navigation; preserve current behavior for disabled/legacy teams and test both.
- SQLite and PostgreSQL lock semantics differ; a uniqueness guard and retry are mandatory, not only an in-memory lock.
- DST, skipped days, unusual 00:01 transitions and timezone changes can shift UTC duration; calculate from local calendar boundaries and prohibit reanchor in phase one.
- A process restart, several workers, or repeated GETs can generate duplicates unless reconciliation is idempotent and bounded.
- Existing manually seeded cycles and issue associations must not be rewritten by enabling cadence.
- A settings mutation may succeed while the browser loses the response: query authoritative settings/interval IDs before retry, never blindly submit twice.

## Approval

This is a **proposal**, not implemented product behavior. The user selected automatic cadence, required weekday selection, chose fixed defaults first, and delegated remaining choices; the conservative choices above are submitted for explicit approval with `exit_plan_mode`. No cadence migration, API, UI, scheduling job or original database change has been made.
